# EZone 2.0 backend comprehensive audit

## Executive summary

Audited clean starting baseline `622a3d1eedfecdc158397df916b40cee77973473` on `codex/background-worker-tests`. Persistent anonymous chat, transactional Random Match, email verification, reporting, and protected HTTP/WebSocket access form a usable core. A two-device prototype can use the existing backend, with Firebase sign-in and refresh performed on the client. A complete returning-user chat experience needs an authenticated room index. The mobile integration must retain the pending reservation ID through Ready confirmation, consume `senderRole`, distinguish REST persistence from WebSocket delivery, and refresh room status explicitly. [API controllers](WebChatEIU/Controllers) · [Mobile chat screen](../Mobile/src/screens/FirebaseChatRoomScreen.js)

Single-instance deployment remains a release constraint. Guarded tests exercise actual HTTP middleware, loopback WebSockets, hosted cleanup, and emulator transactions. They leave real Firebase discovery, refresh, SMTP, deployed indexes, proxy behavior, and device integration unverified. No production system was inspected or contacted. ## Architecture and data ownership

- `Program.Main` initializes Firebase Admin and Firestore with ADC and a hard-coded project, adds Gmail delivery, and hosts the room worker. `AddApiServices` configures scoped feature services, a singleton connection registry that also runs its sweep, singleton moderation, and the Firebase JwtBearer policy. Controllers and hub are mapped in `ConfigureApiPipeline`. Static files are public through middleware and Swagger is gated to Development or Docker. The checked-in solution lists API and offline tests. The integration project is built explicitly. [Startup](WebChatEIU/Program.cs) · [Solution](WebChatEIU/WebChatEIU.sln) · [Integration project](WebChatEIU.IntegrationTests/WebChatEIU.IntegrationTests.csproj)
- `users/{uid}` mirrors Firebase identity with app eligibility. `randomMatchQueue/{uid}` tracks Waiting/Reserved and presence. `matchSessions/{uid}` is an expiring reservation lock. `matchReservations/{id}` owns participant readiness and terminal state. `matchHistory/{pairHash}` prevents repeat pairs. New Ready commits room, pair history and release of owned queue and session state together. Expiry and cancel recheck reservation ownership. Firebase Auth is an external read, so account status can change before the Firestore commit. [Firestore models](WebChatEIU/Models/Firestore) · [Queue service](WebChatEIU/Services/FirebaseRandomMatchQueueService.cs) · [Reservation service](WebChatEIU/Services/FirebaseMatchReservationService.cs) · [Eligibility review](PHASE_2D_1_MATCH_ELIGIBILITY.md)
- `chatRooms/{id}` owns the pair, anonymous roles and lifecycle. `messages/{id}` is a room subcollection. `reports/{id}/evidence/{messageId}` stores a separate copy including sender ID and content. Report and room closure share a transaction. Pending cleanup is historical compatibility and deletes message batches separately from clearing its flag. `roomDecisions` survives as historical schema and test cleanup, with no active decision path. [Report service](WebChatEIU/Services/FirebaseReportService.cs) · [Temporary cleanup](WebChatEIU/Services/FirebaseTemporaryMessageCleanupService.cs) · [Historical model](WebChatEIU/Models/Firestore/FirebaseRoomDecision.cs) · [Lifecycle review](CHAT_LIFECYCLE_REFACTOR.md)
- No active SQL Server or EF Core package was found in the project. Firebase Admin, Firestore, JwtBearer, MailKit and Swagger have active roles. `FirebaseTokenService` is registered without a current caller, `WeatherForecast` has no controller, and the decision DTO has offline tests without an active route. The VS container tooling, tracked IDE metadata, avatar files and historical models merit owner review before removal. Existing production data consumers were outside the audit. [Project](WebChatEIU/WebChatEIU.csproj) · [Startup](WebChatEIU/Program.cs) · [Phase 2B report](PHASE_2B_REPORT.md) · [Decision DTO tests](WebChatEIU.Tests/DTOs/SubmitRoomDecisionDtoTests.cs)

### Source findings and follow-up

- **Report eligibility differs from other room routes.** `CreateReport` checks profile existence, activation and deletion but omits `IsBanned`. The bearer guard rejects disabled Firebase accounts, while a Firestore-only ban with an enabled Auth account can still reach reporting. Decide whether reporting by banned participants is intentional. Add an explicit policy and regression test either way. [Rooms controller](WebChatEIU/Controllers/FirebaseChatRoomsController.cs#L149) · [Bearer session](WebChatEIU/Services/FirebaseBearerSession.cs) · [HTTP ownership tests](WebChatEIU.IntegrationTests/HttpSecurity/HttpJwtSecurityTests.cs)
- **Client error contracts vary.** Invalid requests can return ProblemDetails, strings, `{error}`, `{message}`, or an empty body. Eligibility lookup failures in matching become 409 through `InvalidOperationException`; the central bearer guard maps its own lookup failures to 503. Session's second lookup and verification/resend delivery may still yield generic failures. Resend deliberately returns generic 200 on Firebase Auth exceptions, while the MailKit path is outside that catch. Use status-first handling now and define stable failure codes before polishing the client. [Auth controller](WebChatEIU/Controllers/FirebaseAuthController.cs) · [Session controller](WebChatEIU/Controllers/FirebaseSessionController.cs) · [Match controller](WebChatEIU/Controllers/FirebaseRandomMatchController.cs) · [Message controller](WebChatEIU/Controllers/FirebaseChatMessagesController.cs) · [Mail delivery](WebChatEIU/Services/EmailService.cs)
- **Registration and verification cross system boundaries.** Profile-create rollback is compensating and can fail independently. Successful registration and email failure preserve the user for resend. Verification profile eligibility and activation use separate Firestore operations. These are source-visible failure windows, not observed production incidents. Add recovery/observability and test concurrent profile state changes if account management is introduced. [Auth service](WebChatEIU/Services/FirebaseAuthService.cs) · [User service](WebChatEIU/Services/FirebaseUserService.cs) · [Registration tests](WebChatEIU.IntegrationTests/AuthWorkflows/RegistrationTests.cs)
- **Release configuration needs an explicit boundary.** Normal startup has a fixed project ID and ADC. Development mode alone does not redirect Firebase to the emulator. Development mutation endpoints should stay off any shared live project.
